00Review of edition 2.0 2.1

Edition 2.0 proposes a host-side controller that gives a coding agent a persistent, source-aware debugger for a simulated AVR, and it lists 25 defects it found on the way by reading. The question for this review was whether that holds up when the code is run.

00.1Verdict

  • The architecture is right, and its foundation works. avr-gdb 15.0.50 connected to protosim -d at the pinned revision and did everything the design needs: a source breakpoint in main, stepping by line and by instruction, a RAM variable and a flash constant evaluated by name, a stack frame with file and line, a data watchpoint that reported old and new value, and an interrupt of a running target. It did the same on the ATmega2560. Edition 2.0 could only assume this.
  • The findings are accurate. Of the 25, 16 were re-run here and every one behaved as described; six more were re-read against the source and stand (PS03, PS06, PD03, PD04, PD07, PD10); three were not re-checked (PS04, PD05, PD06) and nothing contradicts them. Six turned out worse than stated (00.3).
  • The most important omission is how a run ends. On Linux, and by the same code path on macOS, a run that stops on --max-steps with the default UART bridge is killed by SIGINT from inside Protosim. The existing MCP tool makes max_steps mandatory, so its normal result is the error path: unparsed text, no failure flag. An agent using the tool as documented never sees a structured result. This belongs at the top of gate G0 (PS11, MC05).
  • The runtime-module part is overtaken. Edition 2.0 treats a loader as future work with a staged plan. A bootloader and module loader now exist as running code in simulation. They implement stage L1 of that plan, without a package format, and add things the plan did not ask for: cooperative loading, and a module refused before the first flash write (17).

00.4What edition 2.0 did not have

  • How Protosim terminates (PS11), that it has no --help or --version (PS12), and eight more defects around bootloaders, HEX loading, UART input and output and reset (PS13 to PS20). Sections 22 and 23.
  • What simavr does differently from a chip (AV02 to AV15). Edition 2.0 warns that writing simulator memory directly is not a loader test. It does not say that simavr also accepts SPM from anywhere, needs no erase, has no read-while-write state and programs a page in no time, so a loader that goes through the real self-programming path can still pass in simulation and fail on a chip. Section 25.
  • Scheduler and serial-path defects in Protoduino beyond PD01 to PD04: polls starve events, CC_EXTERN defines variables, the serial buffers are 16 bytes on every part, the serial process strands output, and more (PD11 to PD22). Section 28.
  • A blocker for the stock Mega. sys/clock.h stops with #error for the ATmega2560, so nothing that uses a timer builds for the profile edition 2.0 starts with (PD17). The first and default profile is now the ATmega328P (13), so this blocks the second profile and not the first release.
  • A scripted conversation as a test. Protoduino now has tools/talk.mjs, a Node 22 program with no dependencies that starts Protosim, types commands at the prompt of a shell, sends files with XMODEM-CRC, resets the part and checks what comes back, and ends with a status. It is what a session tool of the MCP contract (08, 09) would wrap, and its steps (send:, expect:, reset, power) are a first vocabulary for them.
  • Small parts, and a shell that is not on the part. Protoduino now has a port (src/mod/port.h): a process that reads memory, writes memory and calls a function on request, about 470 bytes, with the shell on the PC (tools/port.mjs) taking every name and address from the ELF file. It is the same idea as the debug session of this report, on hardware and without a debugger: a second provider for the inspection tools of section 10. To test it, Protosim got the outside world of a small part: a serial line on two pins, levels and waves into pins, voltages at the ADC and the supply, a log and the duty cycle of output pins, --warp, --run-ms, --dump-eeprom, and the share of time a part sleeps. Three simavr findings came out of it (AV12 to AV14), and a fourth (AV15) when the port learned to load modules into the flash of an ATtiny85. The port opens beyond reading only after a reset through the reset pin, which Protosim gives with SIGUSR1 or --reset-cause pin.
  • The existing agent integration. The repository ships SKILL.md, instructions for language models on using the CLI, and its tests are two PowerShell scripts. Both have to move with the tools (03).
  • Debug information in practice. Source-aware inspection needs an ELF built for it. The Arduino tool chain builds with link-time optimisation by default and the pinned compiler is avr-gcc 7.3; what DWARF such a build carries has to be measured before decoders rely on it (10).

00.6Ideas from this report to take into Protoduino

  • Host decoders for the scheduler (F09, section 10). Finding why the loader's “module started” event disappeared took RAM dumps read by hand; a process-list and event-queue view at a stop would have shown a full queue at once.
  • Generation-checked process handles or purging events on teardown (PD04). Module unload reuses the RAM block of a slot, which is the exact case PD04 describes.
  • A compile-time assertion on the size of a process struct (PD09), extended to the RAM a module slot provides.
  • Honest outcomes (F08). The loader already separates “loaded”, “nobody sent” and “refused, with a code”; the kernel side should report through the same vocabulary of stop reasons this report defines.
  • The evidence bundle (F13) for the loader's 46 scenarios, in place of the ad hoc result files it has now.
  • A removal-safe poll sweep (PD02) before modules can be unloaded while others are polled.

In the other direction, the loader work gives this toolbox three requirements it lacked: binary-safe file transfer to the simulated UART with a real protocol (F15), comparison of simulated flash against an independent reading of the ELF as a pass criterion (18), and a measurement of scheduler fairness, the turns a heartbeat process gets while something else runs, as a runtime metric (18).

01Decision summary

The proposed toolbox lets a coding agent inspect the development environment, build firmware, operate a persistent simulated AVR, connect execution to source, and demonstrate that a change satisfies explicit requirements. Protosim remains an independently useful simulator and CLI. Protoduino remains the embedded runtime and application framework. A shared host-side controller adds GDB and MCP access without coupling either project to a particular language model.

DecisionRecommended direction
Preserve the foundationsRetain the CLI, batch runs, UART bridges, profiling and coverage. Correct misleading outcomes and instrumentation before relying on them for agent decisions. 2.1 Start with how a run terminates (PS11): until that is fixed no outcome can be trusted.
Use GDB as the foundationUse avr-gdb through GDB/MI for source-level debugging; use simavr's remote stub for machine access. Add a narrow simulator channel for cycles, scheduled inputs and profiling. 2.1 The pairing was run and works (07).
Make MCP the first integrationExtend the existing MCP server with persistent sessions. Claude Code, Codex and other compatible clients supply the AI and repository editing.
Keep inspection outside firmwareRead symbols, types and memory on the host. Protoduino-aware decoding does not require a firmware debug agent.
Make setup inspectableAdd protosim --doctor, a doctor alias, JSON output and an equivalent MCP tool. Report capabilities and failures with evidence.
Separate real and virtual targetsStart with stock devices, then qualify expanded memory profiles. Treat 1 MiB flash as an experimental engineering target, not an already validated maximum. 2.1 Decided on 12 November 2026: the stock ATmega328P is the first profile and the default one (13).
Treat the simulator as a model 2.1Record, per result, which behaviour of a real chip simavr does not model (25). A flash-programming result from simulation is evidence of logic and addressing, not of flash discipline or timing.

What makes the combination distinctive. The strongest product opportunity is a complete evidence chain: environment, source revision, build, machine state, observable behaviour, resource budget, regression result. The same tools should support a human debugger, an AI coding agent, automated CI, and measured migration to smaller AVR targets. This is an intended differentiator; no market-wide uniqueness study or comparative benchmark was performed.

Recommended first demonstration

A coding agent diagnoses its tools, builds an unmodified Protoduino example, starts a persistent GDB session, reproduces a scheduler or terminal defect, inspects its cause, applies a source fix, and reruns a saved regression. 2.1 Two defects are now ready-made for it, each with a probe that fails today and a one-line fix: a process that ends is never finalized (PD01), and a process that polls itself stops all events (PD14). Both are reproduced by protoduino/docs/elfloader/prototype/probes/run_probes.sh. Expanded memory can follow without blocking this demonstration; run-time module loading no longer needs to wait for it, because it exists (17).

Important interpretation. Current Protosim -b is a logging observation point, and -s is an instruction trace option; neither is an interactive GDB prompt. Current -w reads configured SRAM addresses at observation points rather than stopping on a write. Preserve these useful batch tools and name new debugger tools precisely. [S1, S2]

The MCP implementation launches a fresh simulator process for each run and waits for process output. Adding -d to that existing one-shot call does not create a usable interactive MCP debugger: the server must separately manage Protosim, GDB, asynchronous stop events and session state. [S4]

The TUI already has element layout, appearance signatures and a command queue. The intended direction is retained vnode/element state with incremental terminal updates; a full AVR screen-cell buffer is not a prerequisite. 05User workflows

A. First use on a development machine. The agent calls doctor before building. It learns which executable paths are selected, whether AVR tools and PlatformIO are available, which source revisions are active, and which profiles are supported. A missing compiler produces a targeted installation/configuration suggestion; a missing optional provider key does not block local MCP debugging. The agent builds a small fixture and performs a bounded GDB handshake smoke check.

B. Explain and fix a stalled process. The agent starts the failing build, replays its input, pauses at a dispatch or termination point, and inspects the scheduler list and event queue using GDB plus the matching source. It distinguishes a process waiting for input from one unable to reach its cleanup state. The resulting patch includes a regression that fails before the change and passes afterward. Reading a process object never requires adding a debug process to Protoduino. 2.1 A third case belongs here: a process that is ready but starved, because another one keeps a poll pending (PD14). The decoder has to show the poll flags and the queue, not only the list.

C. Develop generously, then reduce the target. A controller component passes first on a generous virtual Mega2560 profile. The agent rebuilds for a smaller exact MCU, adapts I/O bindings, measures flash and runtime headroom, and reruns the same externally observable behaviour tests. The terminal UI can remain on a larger target when it is outside the controller component's required contract. The system reports infeasibility rather than silently dropping required behaviour.

D. Investigate a terminal rendering defect. The agent captures UART output and the reconstructed terminal screen, inspects dirty flags and the retained element tree, and reproduces text replacement, shrinking content or node removal. It compares the intended region against the actual terminal state and fixes invalidation or transport behaviour. The host may keep a full terminal buffer; AVR firmware need only retain its tree and update metadata.

E. Develop a loader across repositories. Protoduino exports a documented module ABI; an application repository contains a small module fixture; host tools link it. The agent verifies transmission, flash placement, initialisation, entry, stop and unload. It binds symbols to loaded addresses for debugging and rejects incompatible modules with a reason. A simulator memory write that bypasses the firmware loader is a diagnostic experiment, not a passing loader test. 2.1 The first four of those steps now pass in simulation (17); stop and unload do not exist yet, and the symbol binding is a controller task.

F. Flash and load over the serial line. 2.1 The agent builds a kernel and a module, resets the simulated board into its bootloader, sends the kernel's .elf with XMODEM, waits for the kernel to ask for a module, sends that, and checks three things: flash equals an independent load of both files, the module's process shows up in the decoded process list, and the other processes kept their turns while it loaded.

Definition of a completed task

A reviewable patch, a matching build manifest, preserved acceptance criteria, passing scenario results, measured resource use and explicit remaining limitations. A successful compilation or an enthusiastic model response is not sufficient.

06Architecture

Implement a reusable session/controller library behind the existing TypeScript MCP server. It manages child processes, build identities, operation state, output capture and evidence. A future standalone interface may reuse that library or connect through MCP. GDB provides source-level semantics; Protosim provides simulator-specific control and measurements. [S1, S4, R1]
