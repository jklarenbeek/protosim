A debug_start response returns session_id, build_id, profile_id, capabilities and state_version. Each accepted state mutation increments the version. Operations include a request_id and optional expected_state_version to detect conflicting clients. A single controller owns execution per simulator; parallel tests use separate instances with separate endpoints.

Budgets and stopping. Maintain separate retired-instruction, simulated-cycle and wall-clock limits. A paused GDB poll consumes no retired-instruction budget. Sleeping can advance cycles without retiring instructions. A cycle deadline stops at an instruction/event boundary; report any overshoot rather than promising impossible mid-instruction interruption. Pause/cancel remains serviceable during long runs.

Use stop reasons such as breakpoint, watchpoint, step_complete, uart_match, cycle_budget, instruction_budget, user_pause, cpu_done, cpu_crashed, host_timeout and transport_lost. Keep operation status separate from test verdict: reaching a UART marker does not prove all assertions passed, and reaching a diagnostic budget need not mean the tool itself malfunctioned.

Persistence and recovery. A session survives ordinary MCP calls while the controller lives. It does not automatically survive an agent exit, MCP disconnect or process restart. Default stdio mode cleans up child processes on shutdown. A future daemon mode can support reattachment with ownership and retained manifests. Reset/replay is the initial recovery path; complete snapshots require CPU, RAM, flash, EEPROM, peripheral, timer and input-queue state.

Reset is not a clean slate in simavr 2.1

“Reset and replay” needs three things that do not hold today. avr_reset() discards every pending cycle timer, so whatever the controller scheduled, UART input included, stops for good unless it is registered again (AV08, PS16). It restarts the cycle counter at zero, so cycle stamps and profile totals from before and after a reset do not add up (PS17). And it restarts at simavr's reset_pc, which Protosim never sets, so a board with a bootloader resets into the application (PS18). A replay that needs a reset should start a fresh simulator instance until these are fixed. 2.1 A reset tool also has to take the cause. Firmware and bootloaders branch on MCUSR: the loader work can be built to wait for an upload only after a reset through the pin, and simavr records only power-on and watchdog resets (AV08).

A memory dump is not a complete replay checkpoint. Reverse execution is not supplied merely by enabling GDB; it needs a separately implemented recording/checkpoint mechanism. Do not advertise reverse-step until its semantics are validated.

2.1 Four additions from running the existing server.

  • Never return the whole output. run_simulation puts the complete stdout into full_output: 28,576 characters for a three-second firmware with coverage and call graph. Clients cap the size of a tool result and charge every byte to the model's context. Return a summary and a cursor; keep the log as an artefact.
  • Say what a tool does to state. MCP tool annotations (readOnlyHint, idempotentHint, destructiveHint) carry exactly the retry distinction made above. Set them: inspect and status read-only, continue and UART injection not idempotent, init_arduino_project with overwrite destructive.
  • Declare output schemas. A structured result with a published schema lets a client validate it; it also removes the temptation to parse text, which is how MC02 came about.
  • Judge a child by how it ended, in three parts: exit code, terminating signal, and the stop reason the simulator reported. Node gives a signal and no code for a run that today ends normally (PS11); a controller that looks only at the code misreads it either way.

MCP is the common interface, not a promise that every client supports every optional notification/task extension. Start with ordinary tools, explicit operation polling and stdio. Add remote transport only when required by deployment. Client limits on result size and call duration differ and change; read them from the client's documentation when the tools are implemented.

Which build can be inspected 2.1

  • Debug information is a build decision. The session of section 07 used avr-gcc -Os -g directly. A PlatformIO or Arduino build is different: the Arduino AVR tool chain compiles and links with link-time optimisation, and a PlatformIO release build carries no debug information unless the project selects the debug build type. What a decoder can resolve in such an ELF, static variables like process_list in particular, was not measured here and must be before F09 is designed around it. The likely outcome is a declared debug profile (PlatformIO build_type = debug, or explicit flags without LTO) and a doctor check that the ELF has the types the decoders need.
  • One name, several objects. CC_EXTERN is empty in C, so process_current is defined in every C file that includes process.h and merged by the linker (PD11). A decoder sees one symbol today; with a newer compiler the build fails instead.
  • Modules are easy. A module of the loader work is a fully linked ET_EXEC file at absolute slot addresses. add-symbol-file module.elf registers it without section addresses; remove it on unload.

Rebuilding creates a new build identity. Do not reinterpret yesterday's running binary using today's struct definitions. Dynamically loaded modules need symbol registration and removal on unload. [R2]

14Memory engineering

Flash and code addressing. The pinned simavr has a 32-bit flashend and allocation based on configured size; Mega2560 already uses extended program addressing. A 1 MiB virtual flash is plausible, but is not validated here. Qualify direct/indirect calls, returns, interrupts, high-address constants, ELPM and self-programming. Define implemented RAMPZ/EIND bits and boot-region rules for the virtual profile rather than inheriting physical-device assumptions blindly. [S5, S6]

AVR GCC uses conventions for indirect calls, EIND and linker trampolines. Conventional function-pointer behaviour is not equivalent to a freely widened C pointer. Keep code-pointer/address conversions explicit in the loader and debugger. Near flash reads require appropriate placement or far-access alternatives; inspect the link map. [R5, R8] 2.1 The loader work met both limits in practice. In the ATmega2560's boot section a table in flash lay beyond the reach of LPM, and the bootloader refused every file until the table was read through ELPM. And a module's process type must lie in the first 64 KiB, because process_new() reads it through a near pointer.

Data space and C assumptions. The pinned core uses a 16-bit ramend and classic data-address semantics. Flat 256 KiB or 1 MiB SRAM is outside the initial design: banking or a different architecture would require software support. Expanding within 64 KiB still exposes 16-bit signed arithmetic assumptions, pointer casts, size counters, allocation limits and startup stack configuration. Audit Protoduino's free_mem() and process descriptor sizes before a full-feature profile is accepted. [S5, S7, S10]

One rune per cell is an explicit limitation of the current clipping helper, not general Unicode terminal correctness. Full grapheme shaping is not implied. The earlier 13,440-byte screen-cell estimate is not a requirement for this architecture.

17Native modules 2.1

There are two different deliverables: a bootloader that accepts a linked image and a runtime module loader that manages independently compiled code. ELF32 describes a file format, not a 32-bit CPU requirement. Edition 2.0 planned both in four stages and noted that the existing guide, docs/loader.md, is not an executable design (PD10). Since then a design with running code exists. This section is rewritten around it; the stage plan is kept as the frame.

StageScope of edition 2.0Status

What it adds beyond the contract. The load is one Protothreads v2 thread that does no I/O. The bootloader schedules it at reset; a Protoduino process schedules the same code, where it sits in the boot section, while the system runs. Loading therefore does not stop the scheduler: a heartbeat process took 17,741 turns during a 350 ms load. And the same thread loads through Optiboot's do_spm when the kernel links its own copy, so a board keeps its bootloader.

What simulation cannot show about a loader

The loader goes through the firmware path, as edition 2.0 demands. That is still not hardware evidence, for a reason edition 2.0 does not name: simavr executes SPM from anywhere, replaces a page without an erase, has no read-while-write lockout and programs in no time (AV02 to AV05). A loader that forgot the erase, forgot to re-enable the application section, did not wait, or ran outside the boot section would pass every one of the 41 scenarios. A strict flash mode in Protosim that reports those four would turn blind spots into test failures; it is the most valuable single addition for stage G5.

Full design, measurements and code: protoduino/docs/elf-loader-design.pdf and protoduino/docs/elfloader/. The code sits beside the library at the paths it would have in it; no library source file was changed.

18Verification and evidence

A reproducible experiment bundle. Capture repository commits and dirty-patch hashes; dependency pins; compiler/linker/GDB versions; flags and feature configuration; profile/linker-script hashes; ELF and loadable-image hashes; scenario version; initial memory/peripheral policy; input payloads with actual delivery cycles; stop events; assertions; terminal capture; and resource measurements. Large traces remain artefacts; the model receives focused excerpts and references.

2.1 An independent reader as oracle. The strongest check in the loader work costs one line: after the firmware under test has written flash, compare it with what simavr's own ELF reader produces for the same file. Two implementations that agree on 106 KB of image are unlikely to share a bug. Protosim should offer it as --expect-flash <file.elf> and as the flash_compare tool; it needs honest exit codes to be of use in CI.

Replay reproducibility requires controlling external inputs. Record the cycle when each byte/event is applied, not only host arrival time. Queue host input while paused according to policy. Seed any randomness and define initial RAM/EEPROM values. Different host scheduling or peripheral models may prevent bit-identical replay; report the declared reproducibility level.

Compiler success, debugger stop status and test verdict are separate records. Use reference fixtures and preserved assertions to avoid a model “fixing” the tests to accept a regression. Resource results identify scenario coverage; they are not proof of all possible execution paths. Hardware measurements remain a separate qualification layer.

Performance metrics should separate build duration, simulated cycles per host second, tool latency, trace volume and model tokens. Publish task completion rates only after a reproducible benchmark protocol and baseline exist.

19Providers and hardware

Provider independence. For Claude Code and Codex, the coding client already manages model inference, context and source edits. Protosim MCP exposes deterministic tools and evidence. A future custom client can use OpenRouter, direct APIs or a local model adapter; it should reuse the controller contract. Named models are user examples, not fixed implementation dependencies or promises of availability through a particular endpoint. A standalone provider adapter should declare tool-call support, context/output limits, cancellation and retry behaviour. It records the requested/resolved model identifiers and usage where exposed. It must not silently repeat state-changing tool operations after uncertain delivery. Model-specific prompting stays outside simulator semantics and acceptance tests.

Physical AVR debugging. A supported device and probe may expose on-chip debug access without adding a firmware agent. The chosen GDB-compatible server bridges to the hardware interface. Interface/probe/device support must be verified per target; JTAG, debugWIRE and UPDI cover different AVR families and configurations. [R9]

21Design decisions

DecisionRecommendation / rationale
Execution ownershipOne controller owns GDB and simulator control per instance. A second UI attaches through it, not as an independent command source.
Simulator side channelSmall versioned local endpoint for budgets, scheduled I/O and metrics; keep GDB for source debugging.
Session lifetimeStart with stdio-owned child processes and clean shutdown. Add a reattachable daemon only when a demonstrated workflow needs it.
Target qualification2.1 Decided: the stock ATmega328P is the first profile and the default. Then the stock Mega2560 once Protoduino builds for it; virtual data64k next; 1 MiB flash experimental until its boundary suite passes.
TUI correctnessExplicit dirty/content-generation and removal invalidation; bounded metadata, no mandatory AVR framebuffer.
Module scope2.1 Host-linked ELF in a slot, as built. Decide between the fix-up stream and an on-device relocator before either is started; decide whether a module checksum is stored.
Protocol compatibilityVersion schemas; expose capabilities; preserve existing tools and CLI behaviour except clearly documented bug fixes.
Error semanticsSeparate tool failures, simulator stop reasons and test assertions. Never infer correctness only from exit code or UART text.
One server build 2.1Build the MCP server in one place and stop committing compiled copies; let the package bundle from that build.
Simulator fidelity 2.1Fix the deviations that hide firmware bugs (AV02 to AV05) behind a strict mode in Protosim rather than patching the pinned simavr, and record the mode in the evidence bundle.

Ambitious additions with concrete value. Failure minimisation: reduce a failing input trace to the shortest reproducer while preserving the assertion failure. Resource-frontier search: explore target/configuration combinations and report measured Pareto tradeoffs. Runtime explanation: join process/queue snapshots with the source and terminal at the same stop. Cross-build comparison: highlight changed behaviour and budgets for the same scenario. These are proposed extensions, not current capabilities.

Success measures. Measure time from a clean checkout to the first successful debug session; percentage of scenario runs with complete provenance; reproducibility of failures; verified fix rate on a curated defect set; resource savings without requirement loss; and rate of incorrectly reported success. Compare AI-assisted and manual workflows using the same fixtures, environment and completion criteria. 2.1 The curated defect set now has 59 entries with a trigger each (22 to 28).

The product goal is a distinctive AI toolbox. The defensible claim is the combination of capabilities and measured outcomes; “one of a kind” should remain a positioning ambition until supported by comparative research.
